## 1. TLS 上线（C-01，P0）

### 1.1 现状

deploy/deploy.sh:22-48 已自动感知 TLS：读取 .env 的 DOMAIN，若 certbot/conf/live/<DOMAIN>/fullchain.pem 存在则自动叠加 docker-compose.prod.yml（frontend/backend 不再发布宿主端口），健康门禁改为容器状态 + https 检查；无证书时打印 CRITICAL 警告，REQUIRE_TLS=1 时拒绝明文部署。默认 compose 仍把 frontend 发布到 0.0.0.0:3000（docker-compose.yml:17-18），因此必须执行 enable-tls.sh 或宿主 nginx。目标：浏览器只走 https://<生产域名>，HTTP 301/308；3000 不对公网开放；后端仍只绑 127.0.0.1:8080；/mcp 不经反代暴露。

### 1.2 路线 A：prod overlay（nginx + certbot 容器，推荐）

**优先用一键脚本**（前置：域名 A 记录指向本机，安全组放行 80/443，.env 已设置 DOMAIN 与 CERTBOT_EMAIL）：

```bash
cd /opt/team-portal
# 脚本会：申请/复用证书 → 写回 .env(DOMAIN/CORS__ORIGINS) → REQUIRE_TLS=1 调 deploy.sh
#       → 验证 https/301/3000 关闭，并打印回滚命令。
bash deploy/enable-tls.sh
```

脚本成功后，TLS 拓扑即已生效；之后自动部署（auto-deploy.sh → deploy.sh）会继续识别证书并走 TLS，**AUTO_DEPLOY_OFF 只在变更窗口/回滚时临时使用**，不需要长期保持。

备用手工步骤（仅当 enable-tls.sh 不可用时；不要在生产服务器上触发 build）：

```bash
cd /opt/team-portal
export DOMAIN="<生产域名>"
export EMAIL="<运维邮箱>"
touch deploy/AUTO_DEPLOY_OFF          # 仅变更窗口临时暂停自动部署

docker compose -f docker-compose.yml -f docker-compose.ghcr.yml pull
# 手工申请证书（与 enable-tls.sh 等价；80 端口需空闲）
docker run --rm -p 80:80 \
  -v "$(pwd)/certbot/conf:/etc/letsencrypt" -v "$(pwd)/certbot/www:/var/www/certbot" \
  certbot/certbot certonly --standalone --non-interactive --agree-tos \
  --email "$EMAIL" -d "$DOMAIN"
# 写入 DOMAIN/CORS 到 .env 后，让 deploy.sh 自动叠加 prod
python3 - <<'PY'
import os
p='.env'
d=dict(l.rstrip('\n').split('=',1) for l in open(p) if '=' in l and not l.startswith('#'))
d['DOMAIN']=os.environ['DOMAIN']
cur=d.get('CORS__ORIGINS','')
if f"https://{os.environ['DOMAIN']}" not in cur:
    d['CORS__ORIGINS']=(cur+';' if cur else '')+f"https://{os.environ['DOMAIN']}"
open(p,'w').write('\n'.join(f'{k}={v}' for k,v in d.items())+'\n')
PY
REQUIRE_TLS=1 bash deploy/deploy.sh
```

enable-tls.sh 失败时会打印原因；若已切到一半，按其输出或第 7.2 节回滚。手工步骤结束后确认 `docker compose ... prod.yml ps` 中 nginx/certbot 正常。

### 1.3 路线 B：宿主 nginx（可与当前自动部署并存）

```bash

sudo ln -sf /etc/nginx/sites-available/teamportal /etc/nginx/sites-enabled/teamportal

sudo certbot certonly --webroot -w /var/www/html -d <生产域名> --email <运维邮箱> --agree-tos --non-interactive

sudo tee /etc/nginx/sites-available/teamportal >/dev/null <<'NGINX'

    listen 80;
    server_name <生产域名>;

}
server {
    listen 443 ssl http2;
    server_name <生产域名>;
    ssl_certificate     /etc/letsencrypt/live/<生产域名>/fullchain.pem;

    proxy_send_timeout 1800s;

        proxy_http_version 1.1;

        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;

NGINX

```

路线 B 只是无法使用 prod overlay 时的过渡；enable-tls.sh 成功后应优先走路线 A。每次自动部署后复查 ss -lntp | grep 3000：frontend 可能重新监听 0.0.0.0:3000；DOCKER-USER 规则也要复核。

### 1.4 验收

```bash
curl -sS -o /dev/null -w 'http: %{http_code} -> %{redirect_url}\n' http://<生产域名>/
curl -sSI https://<生产域名>/ | awk 'BEGIN{IGNORECASE=1} /^HTTP\/|^strict-transport-security|^server:/'
curl -sS -o /dev/null -w 'api: %{http_code}\n' https://<生产域名>/api/knowledge/tree
ss -lntp | grep -E ':(3000|8080|443)\b' || true
```

HTTPS 必须 200 + HSTS；HTTP 必须 301/308 或拒绝；未登录 API 必须 401；3000 不应在公网监听，8080 只应在 127.0.0.1。路线 B 还要登录一次，确认「操作日志」记录真实客户端 IP（见 deploy/README-NGINX-MIN.md）。

## 3. 改管理员口令（C-02，P0）

```bash
BASE="https://<生产域名>"
read -rsp "当前 admin 口令: " OLD_PW; echo
TOKEN=$(curl -sS "$BASE/api/auth/login" -H 'Content-Type: application/json' \
  --data-binary @<(printf '{"username":"admin","password":"%s"}' "$OLD_PW") \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')
read -rsp "新 admin 口令（≥12 位，含大小写/数字/符号）: " NEW_PW; echo
curl -sS -X PUT "$BASE/api/auth/change-password" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @<(printf '{"currentPassword":"%s","newPassword":"%s"}' "$OLD_PW" "$NEW_PW")
unset OLD_PW NEW_PW
```

验证：旧口令登录 401；新口令登录 200；旧 token 请求 /api/auth/me 401（TokenVersion 自增）。更新 .env 的 ADMIN__PASSWORD（只在首次建库时生效；置空会在重建库时生成未知随机口令）。不要把新口令写进 shell 历史。首登强制改密目前未实现（User.cs 无 MustChangePassword、AuthService.cs:292-318、AuthEndpoints.cs:123-142）。

## 7. 回滚方案

### 7.1 应用版本回滚

```bash
cd /opt/team-portal
touch deploy/AUTO_DEPLOY_OFF
cat deploy/.deployed_sha
bash deploy/deploy.sh sha-<完整40位commit>
# 验证页脚/接口后恢复；deploy.sh 会自动识别证书并继续走 TLS
rm -f deploy/AUTO_DEPLOY_OFF
```

### 7.2 TLS 回滚

- 路线 A（紧急、临时）：`enable-tls.sh` 结束时会打印回滚命令；对应操作是先用 prod overlay down，再用 base+ghcr up：
```bash
touch deploy/AUTO_DEPLOY_OFF   # 防止 cron 在下一次 deploy.sh 又检测到证书切回 prod
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml -f docker-compose.prod.yml down
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml up -d --no-build
```
  ⚠️ 证书仍在 certbot/conf/live/<DOMAIN>/ 时，下一次 deploy.sh（含 auto-deploy）会自动叠加 prod 再次启用 TLS。若要长期回退明文，必须把证书目录移出检测路径（如 `mv certbot/conf/live/<DOMAIN> certbot/conf/live-disabled-<DOMAIN>`，保留备份）并保持 AUTO_DEPLOY_OFF 直到问题修复；明文 HTTP 不得作为长期状态。
- 路线 B：先备份当前 nginx 配置；sudo rm -f /etc/nginx/sites-enabled/teamportal；sudo nginx -t && sudo systemctl reload nginx；删除 DOCKER-USER 3000 规则（先用 sudo iptables -L DOCKER-USER -n --line-numbers 找行号，再 sudo iptables -D DOCKER-USER <行号>）。证书与 /var/www/html 可保留。自动部署恢复后仍要复查 3000 暴露面。

### 7.3 数据库回滚

优先第 5.2 的 API 恢复（自动安全备份）；API 不可用时按 5.3 tar 恢复。恢复前始终保留当前库副本。

### 7.4 密钥回滚

不允许回退到已泄露的旧 key。新 key 导致故障时修配置/重发新 key；旧值永久作废。
