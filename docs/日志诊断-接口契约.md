### 0.5.4 诊断历史 API（**已冻结**）

```
POST /api/flight-diagnoses        任意已登录用户
GET  /api/flight-diagnoses        列表：admin/部长看全部，普通队员只看自己创建的
GET  /api/flight-diagnoses/{id}   详情：同上 ACL，越权返回 403
```

`POST` 请求体（全部字段必填，服务端做范围校验；`warnings`/`findings` 是摘要，**不要传文档正文**）：
```jsonc
{
  "fileName": "quad_20260617.bin", "sizeBytes": 10249000,
  "records": 229590, "skippedBytes": 0, "durationSec": 362.1,
  "vehicle": "ArduCopter", "vehicleKind": "copter",
  "firmwareVersion": "4.6.2", "versionNumeric": 40602,
  "parseMs": 196, "analyzeMs": 12,
  "decodedTypes": 81, "totalTypes": 81,
  "critical": 0, "warning": 0, "passed": 5, "unknown": 2,
  "warnings": ["最多 20 条，每条 ≤ 500 字"],
  "findings": [{ "ruleId": "vibration_level", "title": "振动超标（IMU0）",
                 "severity": "critical", "status": "fired", "axis": null }]
}
```
→ `200 { "id": 12, "createdAt": "2026-10-12T..." }`

`GET` 列表 query：`limit`(1..100，默认 20) / `offset`(≥0) / `fileName`(精确匹配，可选)
→ `{ "total": 37, "items": [ { ...上面全部字段..., "id": 12, "createdBy": "admin", "createdAt": "..." } ] }`

表 `FlightDiagnosisRecords`：`Id / FileName / SizeBytes / Records / SkippedBytes / DurationSec /
Vehicle / VehicleKind / FirmwareVersion / VersionNumeric / ParseMs / AnalyzeMs / DecodedTypes /
TotalTypes / Critical / Warning / Passed / Unknown / WarningsJson / FindingsJson /
CreatedByUserId / CreatedBy / CreatedAt`。

服务端同时写一条 `LogService.Info("flightdiagnosis", …)`（含 actor、文件名、严重/警告/无法判断数、耗时）
——这就是「运行日志」的服务端落点。

### 0.5.5 第二轮上线后由真实使用反馈暴露的三条教训（**必读，已固化为回归测试**）

#### ① 不适用 ≠ 缺数据（`not_applicable` vs `missing_required`）
线上真实事故：`pid_rate_tracking` 的 `requires` 曾写成 `["PIDR","PIDP","PIDY"]`。
**固定翼默认没有 yaw 速率控制器**（没有 PIDY 日志；`YAW2SRV_*` 是协调转弯阻尼，不是速率环），
于是整条规则被打成"缺少必需消息"，**连 roll/pitch 的分析一起废掉**。
→ 规则修正：`requires: ["PIDR","PIDP"]` + `optional: ["PIDY"]`，**适用性按轴判定**：
Plane/Rover 的 yaw 判 `not_applicable`（附原因），只有 Copter 缺 PIDY 才算 `missing_required`。
**新增任何分轴/分机型规则都必须照这个模式做**，不许把"某机型没有这个环"当成"数据缺失"。

#### ② 能分析就不要拒绝分析（armed 窗口不能退化成空集）
线上真实事故：某份 ArduPlane 日志（85 分钟、确实飞过）报「没有可用的飞行（arm）时间段」，
**三条规则集体只能"无法判断"**。根因：arm/disarm 事件存在但凑不出 ≥1 秒窗口时，
`detectArmedWindows` 返回**空集** → 所有依赖飞行段的规则集体闭嘴。
→ 规则修正：这种情况**退化为全日志**并在 `note` 里如实声明"区间含地面段、结论可能被拉偏"。
**只有连日志时长都拿不到时才允许返回空集。**
关键：分析一个偏宽的区间远比什么都不分析有用——**但绝不能假装它精确**。

#### ③ 客户端的毫秒是小数（DTO 别声明成 int）
线上真实事故：`POST /api/flight-diagnoses` 返回 **400 且响应里没有 detail**。
根因：前端用 `performance.now()` 差值算出的是小数毫秒（实测 `69.89999999990687`），
而 C# DTO 声明成 `int` → **System.Text.Json 绑定失败 → 框架级 400，服务端校验函数根本不会被调用**。
→ 修正：`ParseMs/AnalyzeMs` 声明为 `double`、校验拒 NaN/Inf、落库四舍五入；前端也取整。
**教训**：契约里的数值类型必须用**真实生产者会发出的形状**来定，并且测试要用该形状做用例——
我最初的端点测试用手写整数，所以完全没兜住这个 bug。

### 0.5.7 阈值标定的两条原则（第三轮实测得出，**后续加规则必须遵守**）

**原则一：激励门槛是「比值判据」的补丁，不是「绝对量判据」的。**
比值（如 速度误差/目标速度）在小分母下会天然放大，所以必须先确认指令够大；
但**绝对量**（角度多少度、位置多少米）不管指令多小都是真的没跟上。
实测反例：Copter 有 5 份日志 roll 绝对误差 14.95–30.04°，却因"指令激励 < 2°"被挡在
`insufficient_data` 一侧——**那正是最该被看见的日志**。去掉门槛后它们全部 `fired`
（Copter Roll 整轴由 `passed 38 / fired 2 / insufficient 26` 变为 `passed 59 / fired 7 / insufficient 0`）。

**原则二：阈值必须按机型分档，一份阈值管所有机型是假红根源。**
实测同一指标跨机型差 1–2 个数量级：

| 指标 | Copter | Plane | 一律用一份阈值的后果 |
|---|---|---|---|
| 角度环 Roll 误差 RMS | p50 **0.63°** / p90 5.82° | p50 **19.79°** / p90 51.3° | Plane **7/9 全 fired** |
| 位置/航迹横向偏差 | p50 **0.065 m** / p90 ≤0.16 m | p90 **51.6 m** | Copter 永不触发、Plane 几乎全 fired |
| 高度偏差 | p90 **0.15 m** | p50 **18.2 m** | 同上 |
| TECS 空速误差 RMS | — | min **2.47** / p50 5.42 m/s | 初值 warn=2 让 **7/7** 全部触发 |

最终采用值（均有实测分位数依据，写在 `thresholds.ts` 注释里）：
Plane 角度环 roll `40/55`、pitch `20/25`；位置 XT `20/45`、AltE `30/50`；
Copter 位置/高度 `0.5/2.0` m；TECS 空速 `8/15`、高度 `10/25`、油门饱和 `0.8/0.95`、俯仰饱和 `0.1`。

⚠️ **诚实声明**：这批日志**没有人工故障标注**，所以阈值是「**不误报 + 抓最差**」定出来的，
**不是真值标定**。全部 76 份语料上的最终分布：
`passed 414 / not_applicable 87 / insufficient_data 104 / fired 30 / missing_required 94`，
`not_applicable` 全部来自**结构性缺失**（Copter 无空速 66、Plane 无 PSC\* 9、Plane 无航向角指令 9、Rover 3），
语料测试用白名单钉住这条性质，**不允许把"缺数据"混成"不适用"**。

**Rover 档位仍是空白**（落 `default` 5/15 m）：唯一那份 Rover 日志 `NTUN.XTrack` 恒 0 无法标定。
代码里已留可追溯注释——**不要凭感觉补档**，等有带航迹的真实日志再按分位数补。

### 1.5 实测标定结果 + **对方案 v2 的修正 C1–C3**（重要）

用 pymavlink 对 6 份真实日志做了阈值标定（脚本：见提交历史中的 `flog_calibrate.py` 思路，
结论已固化进 `web/lib/flightlog/analysis/thresholds.ts`）。

**记录率实测（决定性）**

| 消息 | quad (Copter 4.6.2) | Plane 日志 | 结论 |
|---|---|---|---|
| `PIDR/PIDP/PIDY` | **10.0 Hz**（dt=100 ms） | 10.0 Hz；`fw_0619` 为 25 Hz | Nyquist 仅 5 Hz |
| `VIBE` | 10 Hz，3 个 IMU 实例 | 同 | 振动等级可用 |
| `IMU` | 约 22.6 Hz/实例（24561/3/362s） | 同量级 | 频率域几乎无信息量 |
| `FTN1` | 有，但 SnX/SnY/SnZ = -0.3/-1.8/0.0 dB | 同 | **机上未检出显著窄峰** |

**修正 C1（硬伤）：方案 v2 的旗舰示例「rate error 主峰 6.2 Hz」从 PID 日志里测不到。**
PID 消息默认 10 Hz → Nyquist 5 Hz，6.2 Hz 会混叠成 3.8 Hz。
已用单测固化：`tests/flightlog-spectrum.test.ts` 断言 10 Hz 采样下 6.2 Hz 被混叠。
**要看 6.2 Hz 必须开 `INS_LOG_BAT_MASK=1`，由飞控自身 FFT（FTN1/FTN2）给出。**

**修正 C2（硬伤）：方案 v2 的 PID 频谱判据是误报机器。**
实测「0.8–4 Hz 频带能量占比」在健康与故障日志间完全重叠：

## 3. 关键实现约定

### 3.1 解析器（`web/lib/flightlog/dataflash/`）

- 纯函数 `parseDataflash(bytes: Uint8Array, opts?): ParseResult`，**可在 vitest 直接调用**
  （不依赖 Worker）。Worker 只是薄壳。
- 只解码白名单消息（至少：`FMT, FMTU, UNIT, MULT, PARM, VIBE, PIDR, PIDP, PIDY, RATE, ATT,
  IMU, FTN1, FTN2, RCOU, CTUN, POWR, BAT, GPS, EV, MODE, ARM, MSG, VER`）。
- `messageCounts` 必须**统计到所有消息**（含未解码），否则缺失判定会误报。
- 多实例消息按实例号拆 `Series`（`VIBE.IMU`、`IMU.I`、`GPS.I`）。
- 值按 `FMTU`+`MULT` 换算为标称单位；拿不到换算表时保持原值并在 `warnings` 记一条。
- 截断/CRC 异常：跳过该记录、累计到 `warnings`，**不要抛异常中断整个文件**。
- 目标性能：9.8 MB 样本 < 500 ms（pymavlink 全量 1.16 s 是基线，我们只解码子集应更快）。

### 3.2 版本感知

- ArduPilot 版本从 `MSG`/`VER` 横幅取（`ArduCopter V4.6.2 (…)`）。
- 数值版本口径 `major*10000+minor*100+patch`（见 `version.ts`），全项目唯一。
- 规则 `appliesTo` 不匹配 → `status="not_applicable"` + `note` 说明，例如
  「本规则要求 ArduPilot ≥ 4.4（需要 PIDR 逐项日志），当前 4.0.3」。

### 3.3 规则输出纪律（**最容易做错的地方**）

| 情况 | 必须输出 |
|---|---|
| 缺 `VIBE` 消息 | `status="missing_required"`, `severity="unknown"`, `note` 写明缺什么 |
| 平台/版本不匹配 | `status="not_applicable"`, `severity="unknown"` |
| 窗口内样本 < 最小样本数 | `status="insufficient_data"`, `severity="unknown"` |
| 检查执行且正常 | `status="passed"`, `severity="ok"` |
| 触发 | `status="fired"`, `severity` 按阈值分档 |

**禁止**：把 unknown 情形写成 `passed`。UI 上「无法判断」和「通过」是两回事。

⚠️ **实测踩过的坑（已修，务必不要回退）**：滤波规则最初在"振动测不出来"时走了"振动在阈值内 → 无需启用陷波 → 通过"这条路，
等于**把未知说成了通过**。现在 `decideNotch` 在 `vibrationUnavailable !== null` 时返回
`vibrationUnmeasurable` → `status="insufficient_data"` / `severity="unknown"`。
**推论：任何"因为 A 正常所以 B 无需处理"的推断，都必须先确认 A 真的被测到了。**

### 3.4 阈值来源必须有依据

每条规则的阈值必须能指到官方文档（写进 `docLinks`）。本切片采用：

| 规则 id | 阈值 | 来源 |
|---|---|---|
| `vibration_level` | `VIBE.VibeX/Y/Z` 标准差 ≥ **30** m/s² 严重、≥ **15** 警告；`Clip` 增量 ≥ **1** 直接严重 | ArduPilot 振动文档，并经 6 份真实日志标定（§1.5） |
| `pid_rate_tracking` | 激励门槛 **10 °/s**；`Err/Tar` ≥ **1.0** 严重、≥ **0.5** 警告；最少 **100** 个样本 | 实测标定（§1.5）+ 官方调参指引；**不是**频谱阈值，理由见修正 C2 |
| `filter_notch` | 机上 FFT 参考 **25 dB**（`FFT_SNR_REF` 默认）；仅当振动 ≥ 15 m/s² 或 clip > 0 才允许建议陷波；`INS_HNTCH_FREQ` 与实测主峰偏差 > **20%** 告警 | ArduPilot 陷波 / FFT 文档 |

阈值集中在 `analysis/thresholds.ts`，**不得散落在规则里**，便于日后按真实日志校准。

### 3.5 图表

- uPlot（新依赖，Lead 只加一次到 `web/package.json`）。分析视图**不用** recharts。
- 规则通过 `Finding.charts` 声明要看什么；UI 不写业务判断。
- 不降采样：`Err` 峰值就是证据，削峰等于毁证据。
- 频谱由规则算好放进 `SpectrumData`，UI 不重算 FFT。

## 附：0.5.8 跟踪质量分级 + 速率环 P/I/D/FF 精调建议（第四轮，用户要求）

用户原话：「**要给出每一个环的 pid 和 ff 精确调优的建议，不是说通过就行了，明明很多调优还要很大改进空间，跟踪效果不好**」。

### 分级取代二元「通过」
`A/B` 才算 `passed`；**`C` = `fired` + `warning`**，现象里必须写「能跟但偏松，仍有明显改进空间」；`D` = `critical`。
门槛由 **76 份语料实测分位数**定（仅统计高指令样本 `|Tar| >= 0.3·RMS`）：

| | p10 | p25 | p50 | p75 | p90 |
|---|---|---|---|---|---|
| `Err/Tar` | 0.044 | 0.209 | **0.575** | 0.967 | 1.121 |
| `Tar→Act` 滞后（采样） | 0 | 1 | **2**（10 Hz → 200 ms） | 5 | 10 |

分档：`A < 0.20`、`B < 0.40`、`C < 0.70`、`D >= 0.70`。

### 关键物理结论（决定建议的**顺序**）
中位数两行自洽：`0.5 Hz` 指令 + `200 ms` 纯延迟 → 误差 ≈ `2π×0.5×0.2 = 0.63` ≈ 实测 `0.58`。
⇒ **这批日志的速率环误差主要由相位滞后贡献，不是 P 不够**。
FF（前馈）正是消滞后的手段且**不引入相位滞后**，加 P 会 → **滞后主导时 FF 排在 P 之前**
（与官方"先滤波→P→D→I→FF"的首次整定顺序不冲突：那是首次整定的顺序，这里是由数据决定下一步改哪个）。

### FF 起点值的推导（**可复算**）
```
FF ≈ P_gain × 2π f τ          （纯延迟近似；f = 指令主频，τ = 实测滞后秒数）
建议值 = 该式结果的一半，且不超过 P_gain 的 60%
```
每个数字写进 `evidence`/`reason`，并**必须声明假设**：「依赖纯延迟 + 单一主频近似；真正的增益需要阶跃响应或系统辨识，日志里没有」。
其它签名：`|mean(I)|/IMAX > 0.15` → 先查重心（不是只说"调 I"）；`RMS(D)/RMS(Err) > 0.5` → D 在放大噪声。
⚠️ `Dmod` 在这批语料里恒为 1.0，**不能当签名用**（已实测）。

### 「通过也带建议」
用户明确说"不是说通过就行了"，所以 **A/B 级的 Finding 同样附带 `suggestions`**，`note` 说明是起点值。
UI 的 `FindingCard.hasDetails` 已包含 `suggestions.length > 0`，无需改动即渲染。
