# 权限管理设计（可配置权限矩阵）

> 目标：管理员在后台勾选「角色 × 权限」就能调整全队可用的功能与操作，不用改代码发版。
> 默认矩阵写在代码里（受评审与 CI 保护），数据库只存**覆盖值**；删行即恢复默认，改完立即生效。

---

## 一、设计目标与原则

- **默认矩阵在代码里**：默认权限属于产品语义，要能被代码评审、diff 和 CI 看见；存进数据库会被测试数据与手改污染。
- **数据库只存覆盖**：表 `RolePermissions` 里只有管理员真正改过的格子，没行 = 用代码默认；表小、语义明确，以后调整默认值不会被历史数据锁死。
- **删行即恢复默认**：保存时「与当前默认一致」的改动直接删行，所以恢复默认不需要数据迁移，也不会留下"伪覆盖"。
- **前端隐藏不是安全边界**：`can()` 只决定菜单/按钮显示；每个权限点在后端注册 `perm:<key>` 策略，直接调接口一律 403。
- **改完立即生效**：授权处理器是同步的，因此矩阵常驻 `PermissionService` 内存；任何保存/恢复后立刻 Reload，不重启、不重新登录。
- **不允许把系统锁死**：明确拒绝收回 admin 的 `admin.permissions.manage`，未知角色/权限也拒绝写入，避免脏数据造出"假权限"。

## 二、总体架构

```
PermissionCatalog（代码：44 个权限点 + 三角色默认矩阵）
        │  合并：默认 ⊕ 覆盖（Allowed=true 加，Allowed=false 减）
        ▼
PermissionService（单例，内存矩阵 _matrix）
        │
        ├── PermissionHandler ← 策略 perm:<key>（Program 启动时按目录逐个注册）
        ├── GET /api/me/permissions → PermissionsProvider.can() → 侧栏/按钮
        └── PUT /api/admin/permissions、DELETE /api/admin/permissions/{role}
                    │  SaveAsync / ResetRoleAsync → ReloadAsync
                    ▼
            RolePermissions（SQLite：只存覆盖行）
```

兜底链：数据库覆盖 → 代码默认 → 空集合。Reload 读库失败时沿用旧矩阵（首次启动则用纯默认矩阵），不会因为一次数据库抖动把所有人锁在门外。

## 四、默认矩阵

默认矩阵就是上表「默认拥有」列，代码里按角色派生（`PermissionCatalog.BuildDefaults`）：

```
member (18)  = 上表标「全员」的全部（含 A/B/C 三档物料的查看权限）
部长   (35)  = member ∪ 上表标「部长 + 管理员」的 17 项
admin  (44)  = PermissionCatalog.All 全量
```

- admin 用**全量**而不是逐项枚举：新增权限点默认就给管理员，避免"功能加完，管理员自己反而进不去"。
- 部长需要**显式列出**：给部长扩权必须出现在 diff 里被评审，不能因为新增权限点悄悄扩权。
- 角色字符串与 JWT 的 role 声明、`AdminService` 的角色白名单完全一致，只能是 `member` / `部长` / `admin`；管理页列顺序即 `PermissionCatalog.Roles`。

运行期合并：`matrix(role) = Defaults(role) ⊕ {Allowed=true 的覆盖行} − {Allowed=false 的覆盖行}`。

| 表 / 迁移 | 说明 |
|---|---|
| RolePermissions | 复合主键 (Role, Permission)；Allowed=true 授予 / false 收回；UpdatedByUserId、UpdatedAt 留痕 |
| AddRolePermissions（20261120123113） | 唯一一次迁移；**不写种子数据**，默认值永远不落库 |

## 五、接口清单与权限

| 方法 | 路径 | 所需权限 | 用途 |
|---|---|---|---|
| GET | /api/me/permissions | 仅登录 | 当前角色 + 权限 key 数组；前端 `can()` 的数据源 |
| GET | /api/admin/permissions | perm:admin.permissions.manage | 角色、分组、当前矩阵、默认矩阵、覆盖行 |
| PUT | /api/admin/permissions | perm:admin.permissions.manage | 批量保存变更，body = `[{role, permission, allowed}]` |
| DELETE | /api/admin/permissions/{role} | perm:admin.permissions.manage | 恢复某角色全部默认（删该角色所有覆盖行） |

- `/api/me/permissions` 不能用 perm 策略自保护：用户还没拿到权限清单时就需要它，用权限点挡会形成死锁（登录后永远拿不到清单）。
- `GET /api/admin/permissions` 同时返回 `matrix`（合并后结果）、`defaults`（代码默认）与 `overrides`（原始覆盖行）：管理页用前三者渲染表格与「改动 N 项」，逐格的"已是覆盖值"角标暂未做。
- PUT 校验：空数组或 >500 条 400；未知角色/权限 400；收回 admin 的 `admin.permissions.manage` 400。写入后按 `permission.update` 记审计（条数 + 前 20 条明细）。
- DELETE 目前**不写**审计日志（仅 PUT 记）；需要完整追溯时查覆盖行的 UpdatedAt / UpdatedByUserId。
- 接入进度：本次先落地管理端权限接口（已用 `perm:admin.permissions.manage`）与侧栏导航过滤；其余业务端点按模块分批迁移，逐组把 `AdminOnly` / `StaffOnly` 换成对应的 `perm:<key>`，不涉及数据结构变更。

## 六、前端结构

| 文件 | 作用 |
|---|---|
| web/app/(protected)/layout.tsx | 挂 `PermissionsProvider`，登录后所有页面共享一份权限 |
| web/components/permissions/PermissionsProvider.tsx | 拉 `/api/me/permissions`；`usePermissions()` → `{ role, permissions, ready, can, refresh }` |
| web/components/layout/Sidebar.tsx | `NavItem.perm` 过滤菜单；分组内条目全被过滤时整组隐藏 |
| web/components/admin/permissions/PermissionMatrix.tsx | 矩阵勾选、只提交差异、按角色恢复默认 |
| web/app/(protected)/admin/permissions/page.tsx | 管理页外壳（标题 + 说明） |

`can()` 语义：`ready === false`（首次请求未返回）时一律返回 true。原因是一律按无权限渲染会让整块导航先消失再出现，用户会误以为掉权限；拿到服务端结果后严格按集合判断。刷新页面或 `refresh()` 后即可看到新菜单。

## 七、在代码里接入一个新权限点

1. **目录加 key**：在 `PermissionCatalog.All` 加 `new("模块.对象.动作", "分组", "中文标签", "可选说明")`。分组决定管理页归类，desc 会显示在权限名下方。
2. **端点加策略**：给接口或 `MapGroup` 挂 `RequireAuthorization("perm:模块.对象.动作")`。`Program.cs` 启动时会为目录里的每个 key 注册同名策略，**不要**再手写 `AddPolicy`。
3. **前端用 can()**：菜单项加 `perm` 字段，或按钮处 `{can("模块.对象.动作") && <按钮 />}`。这层只影响显示，安全判断必须留在后端。
4. **补默认矩阵**：成员该有的加进 `BuildDefaults` 的 member 集合，部长该有的加进 staff 集合（staff 已含 member）；admin 自动拿全量。漏补 = 默认谁都没有。

接入后补一条测试（策略注册 + 端点 403/200），并把新行加进本文第三节清单。删除权限点要先清覆盖行再删目录 key，否则表里会留下永不生效的旧行。

## 八、管理页操作说明

入口：侧栏「系统 → 权限管理」（/admin/permissions），需要 `admin.permissions.manage`。没有该权限的人打开页面只会看到加载失败提示「仅具备『权限管理』权限的人可访问」。

- **勾选**：行=权限点（带 key 与说明），列=成员/部长/管理员。勾选只改本地草稿，顶部显示「改动 N 项」；无改动时「保存」按钮禁用。
- **保存**：只提交与当前矩阵不同的格子（PUT 数组）。与默认一致的格子由服务端换算成删覆盖行，所以不需要"另存默认"。
- **恢复某角色默认**：点角色表头的 ↺，二次确认后 DELETE 该角色全部覆盖行，矩阵回到代码默认。
- **不能收回 admin 的权限管理**：`admin` 列这一格被勾掉仍会提交，但后端返回 400（"不能收回管理员自己的『权限管理』权限，否则将无人能再修改权限"），保存失败并提示。这是刻意的硬保护，避免把自己锁在门外。
- **生效范围**：后端立即生效（下一次请求就按新矩阵授权）；菜单需要用户刷新页面重新拉 `/api/me/permissions` 才更新。改动不触碰 JWT，所以已登录用户无需重新登录。
- **边界**：矩阵只控制"能不能用这个功能/做这个操作"，不改变部门数据范围（见第九节）。

## 九、已知边界

- **数据级可见性不在矩阵里**：物料/资料能看哪些行、知识库 ACL 的部门范围、部长只能管本部门成员等，仍由各接口自己的逻辑判断。可能出现"有功能权限但列表为空"，这是预期——把行级规则塞进矩阵会组合爆炸且难以审计。
- **自定义角色暂不支持**：角色是 JWT 的 role 声明 + 常量 `PermissionCatalog.Roles` + `AdminService` 白名单 + 前端 `ROLE_LABEL` 四处对齐的固定枚举，新增角色属于认证层需求。
- **角色变更需重新登录**：矩阵调整立即生效；但改某人的角色/部门会自增 TokenVersion 使旧 token 立即失效（安全设计），当事人需重新登录；用户端菜单也要刷新页面。
- **单实例内存矩阵**：保存只 Reload 当前进程。当前是单容器部署所以成立；水平扩容需要加广播或定期轮询，否则各副本权限不一致。
- **覆盖行不自动清理**：删权限点后，库里残留的覆盖行不会报错也不会生效（策略只按目录注册），但会让"覆盖列表"变脏。
- **前端隐藏不是权限**：隐藏的按钮仍可被直接构造请求调用，最终由 `perm:<key>` 策略返回 403。
- **审计粒度**：一次保存一条 OperationLog（含条数与前 20 条明细），不是逐格历史；要精确追溯靠 `RolePermissions.UpdatedAt / UpdatedByUserId`。

## 十、测试与验证

- **后端单元（PermissionService）**：默认矩阵按角色生成；覆盖行 add/remove 合并；与默认一致的改动不落库（删行）；ResetRole 清空该角色覆盖；Reload 读库失败沿用旧矩阵。
- **后端集成**：`GET /api/me/permissions` 返回角色与集合；无权限用户访问 `/api/admin/permissions` 403；PUT 未知角色/权限、收回 admin 权限管理 → 400；PUT 后用 GET 看到新矩阵；DELETE 某角色后回到默认。建议新增 `tests/api/PermissionsTests.cs`（截至本文写作时该文件尚未建立，迁移端点时一并补）。
- **前端**：Vitest 覆盖 `can()` 的 ready 语义与"只提交差异"的纯逻辑；`npx tsc --noEmit`、`npx eslint .` 必须干净（禁 any）。
- **手动 smoke**：用 admin 与 member 两个账号。admin 取消 member 的 `content.study.view` → 成员刷新页面后侧栏「学习库」消失，直接访问 /study 或调接口返回 403；点 ↺ 恢复默认后功能回来。
- **命令**：`dotnet test tests/api`、`cd web && npx tsc --noEmit && npx vitest run`。
- 注意：本机部分沙盒会拦截子进程（esbuild / testhost 报 EPERM 或「拒绝访问」），此时 vitest / dotnet test 需在普通终端或 CI 中运行；tsc 与 eslint 不受影响。
