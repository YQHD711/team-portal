### critical

#### 1. 生产管理员口令（已打码）硬编码在公开仓库文档中，且与线上口令一致

- **位置**：`docs/交接文档.md:141,146-148`；`CLAUDE.md:25`；`deploy/basic-deploy.sh:56-57`；`src/TeamPortal/Services/AuthService.cs:60-84`
- **证据**：
  - `docs/交接文档.md:141`：``默认管理员账号/口令（值已打码）。``，4.6 节进一步给出可直接复制粘贴的线上登录命令（生产地址已改为占位）。
  - `CLAUDE.md:25`：原文为默认管理员账号/口令（值已打码；该文件在 HEAD 中被 git 跟踪）。
  - 用仓库内 `data/teamportal.db` 的 admin 行哈希（值已打码）以 BCrypt.Net-Next 校验：默认口令 => True，其他测试口令 => False。
  - GitHub API 返回该仓库 `"private": false, "visibility": "public"`。
- **可达性前提**：无需任何前置条件、无需认证。打开公开仓库即可同时拿到口令与生产地址；对线上 POST /api/auth/login（默认账号/口令）实测返回 509 字符 JWT。
- **修复建议**：
  1. 立即在「系统设置」轮换 admin 口令，并检查审计日志有无异常登录；
  2. 从 `docs/交接文档.md`、`CLAUDE.md`、`deploy/basic-deploy.sh` 删除默认口令与“生产默认账号”表述，改为指向密码管理方式；
  3. 种子管理员改为首登强制改密，或只允许 `ADMIN__PASSWORD` 环境变量注入、缺失即跳过创建（`Program.cs:46` 已有随机兜底）；
  4. 历史提交需 `filter-repo` 清理，或接受其为公开事实并永久作废该口令。
- **验证结论**：`confidence=certain`、`verdict=confirmed`。哈希校验与线上实测登录均成功。唯一不精确处是“仓库自带的生产库”表述失当（该 DB 未被跟踪，含本地测试账号），但不影响结论——线上可达性已用真实登录直接证实。

### high

#### 2. MCP `material_checkin` 工具缺角色校验：任意登录成员可代他人归还领用、回补库存

- **位置**：`src/TeamPortal/Mcp/MaterialTools.cs:48-50` 与 `src/TeamPortal/Services/MaterialService.cs:198-205`
- **证据**：MCP 侧完全无校验：

  ```csharp
  [McpServerTool(Name = "material_checkin")]
  public async Task<object?> Checkin(int requestId, string condition, bool hasPhoto, string? testNotes = null, string? photoUrl = null)
      => await _material.Checkin(requestId, GetUserId(), condition, hasPhoto, testNotes, photoUrl);
  ```

  同一动作的 HTTP 端点却要求 staff（`src/TeamPortal/Endpoints/MaterialEndpoints.cs:182-183`）：

  ```csharp
  var (role, _, _, userId) = await GetCtx(user, db);
  if (!IsStaff(role)) return Results.Problem("仅管理员和部长可操作", statusCode: 403);
  ```

  服务层也不做归属/角色兜底，只校验状态（`MaterialService.cs:201-205`）：`req is null || req.Status != "approved"` 即返回，随后无条件回写库存。MCP 端点仅要求登录（`Program.cs:408`：`app.MapMcp("/mcp").RequireAuthorization();`），`McpAuth.cs:8-12` 自述“任意登录成员都能通过 MCP 调用他本无权执行的运维/管理操作”。
- **可达性前提**：任何持有效 JWT 的普通队员即可对 `/mcp` 发 JSON-RPC 调用 `material_checkin`，`requestId` 为自增整数可枚举，跨部门同样有效。`isStaff` 分支是 HTTP 路径独占的。**注意**：`deploy/nginx.prod.conf:67/79` 只转发 `/` 与 `/api/`，因此“任意成员可访问 `/mcp`”成立的前提是该端点被单独暴露（其设计用途正是给外部 agent）。
- **修复建议**：在 `MaterialTools.Checkin` 开头加 `if (!McpAuth.IsStaff(_http)) return McpAuth.Forbidden;`，并按 `MaterialEndpoints` 口径补部门校验；更稳妥的是在 `MaterialService.Checkin` 内强制校验 `checkedByUserId` 为原单申请人所属部门部长或 admin（服务层兜底，防其他调用方再犯）。
- **验证结论**：`confidence=certain`、`verdict=confirmed`。`MaterialTools.cs:48-50` 是同文件唯一无任何 `McpAuth` 断言的写工具（:26/:30/:34/:41/:54 均有校验）。属真实 broken function-level authorization，high 合理。

#### 3. MCP `material_checkin` 缺少 staff 校验（agent 域独立复核）

- **位置**：`src/TeamPortal/Mcp/MaterialTools.cs:48-50`
- **证据**：与第 2 条同源。另核实 `McpAuth.cs:30` 已提供 `IsStaff` 却未在此使用；`Program.cs:103-107` 只有 `AdminOnly`/`StaffOnly` 两个命名策略、无 FallbackPolicy；全仓 grep 无其他中间件对 `/mcp` 加角色限制。
- **可达性前提**：任何已登录普通成员即可触发；`condition="damaged"` 还能把物料置为 `broken`。
- **修复建议**：`=> !McpAuth.IsStaff(_http) ? McpAuth.Forbidden : await _material.Checkin(...)`；或服务层校验 `checkedByUserId` 为 staff 或归属人。建议为每个 MCP 工具补一条“非 staff 调用必须被拒”的测试，避免同文件权限守卫继续漏项。
- **验证结论**：`confidence=certain`、`verdict=confirmed`。可达性同样受 `/mcp` 是否对外暴露影响，代码缺陷本身确定成立，维持 high。

#### 4. Wiki 任务删除时用未校验的 `ProjectName/TargetFolder` 拼回收站路径（路径穿越）

- **位置**：`src/TeamPortal/Endpoints/WikiEndpoints.cs:152,153,155`
- **证据**：删除端点直接用任务行字段拼路径后交给回收站执行 Move：

  ```csharp
  var kbRoot = knowledge.BasePath;
  var folders = new[]
  {
      Path.Combine(kbRoot, task.TargetFolder, task.ProjectName),
      Path.Combine(kbRoot, task.TargetFolder, $"{task.ProjectName}_EN"),
  };
  db.TrashItems.Add(trash.StashPaths(folders, $"Wiki 项目：{task.ProjectName}", "WikiTask", uid, actor, row: task));
  ```

  `TrashService.Files.cs:47-58` 对收到的绝对路径不做越界校验，存在就 `Directory.Move`/`File.Move`。`ProjectName` 来源只有非空校验（`WikiEndpoints.cs:18`），只对 `TargetFolder` 过 `CanAccess`（:21-23）。仓库其它同类判断均带分隔符（`WikiEndpoints.cs:342-345`、`FirmwareCacheService.cs:52`、`BackupService.cs:182`），只有这里既无 `ResolvePath` 也无 segment 白名单。
- **可达性前提**：需要 staff（admin 或「部长」）。① `POST /api/wiki/submit-git`，`ProjectName` 填 `../../teamportal.db`、`TargetFolder` 用 `"公共"` 即可通过 `CanAccess`；② 用返回的 `task.Id` 调 `DELETE /api/wiki/tasks/{id}`。rooted 路径（如 `C:\...`）会覆盖 `Path.Combine` 前缀，可达任意路径。配置 `Knowledge:BasePath=../../data/knowledge`、DB 指向 `/data/teamportal.db` 时，`公共/../../teamportal.db` 正好指线上 SQLite 主库。**这是普通 staff 就能触发的破坏性操作，不只是管理员。**
- **修复建议**：拼 stash 路径前用 `knowledge.ResolvePath` 做“必须落在知识库根内”校验，并对 `ProjectName/TargetFolder` 做 segment 白名单（禁止 `.`/`..`/分隔符/盘符，参照 `WikiGeneratorService.IsSafeCatalogPath`）；同时让 `TrashService.StashPaths` 内部也做兜底校验，避免任何调用方漏判。
- **验证结论**：`confidence=certain`、`verdict=confirmed`。上游无防护：提交端点只做非空校验（无 InputSanitizer，全仓仅 Exam/Material 使用），失败任务保留不删行，DELETE 只校验角色。仅“搬到回收站”属可恢复，但可移走线上主库造成服务中断，high 恰当。

- **位置**：`src/TeamPortal/appsettings.json @ 6be407b:23,30-32`；`src/TeamPortal/appsettings.Development.json:10,13-15`；`Services/BaiduNetdiskService.OAuth.cs:12-13`

#### 6. 库存归还数量无上界，可写出越界值导致 `InventoryItems` 整表读取抛 `OverflowException`

- **位置**：`src/TeamPortal/Endpoints/InventoryEndpoints.cs:338-353`
- **证据**：归还端点只校验下界，创建/修改端点的 `1_000_000` 上限在此缺失：

  ```csharp
  if (req.Quantity <= 0) return Results.Problem("Quantity must be positive", statusCode: 400);   // 343
  var updated = await db.InventoryItems.Where(i => i.Id == id).ExecuteUpdateAsync(s => s
      .SetProperty(i => i.Quantity, i => i.Quantity + req.Quantity)   // 348-352
      .SetProperty(i => i.UpdatedAt, DateTime.UtcNow));
  ```
